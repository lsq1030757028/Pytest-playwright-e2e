# M1.0 Memory Benchmark & Threat Model — SPEC Test Design

> Test Design ID: `TD-M1.0-MEMORY-SPEC`  
> Goal: Issue #20  
> Change profile: `DEV2` for the SPEC; future Memory runtime is `DEV3`

## 1. Test objective

This test design verifies that the M1.0 SPEC is complete, internally consistent, machine-readable, aligned with the active roadmap and GitHub Development SSOT, and sufficiently strict to guide later DEV3 implementation without silently relaxing protected controls.

The subject under test is the **specification boundary**, not a Memory runtime.

## 2. Risks introduced by this change

| Risk | Evidence response |
|---|---|
| The SPEC claims to cover Memory but omits a critical threat | Machine-check the required threat IDs and protected assets |
| Markdown and YAML drift apart | Validate identifiers, gates, scenario families and module boundaries from YAML; PR review compares narrative intent |
| The SPEC mechanically demands every test layer | Keep test selection tied to threats and observable boundaries |
| Candidate memory is accidentally treated as authority | Assert forbidden automatic promotions and authority lifecycle |
| Value metrics allow a safety regression | Assert efficiency cannot compensate for safety failure |
| Benchmark claims improvement through cherry-picking | Require fixed catalog, repetitions, paired dimensions and holdout controls |
| M1A/M1B scope becomes vendor-specific | Assert forbidden database, embedding and retrieval choices |
| SPEC work is mistaken for runtime completion | Assert roadmap remains `FOUNDATION_BASELINE / NOT_READY` and M1.0 remains the current next unit |
| Later agents bypass SPEC-first | Link `AGENTS.md`, status, roadmap and Goal Issue in PR evidence |

## 3. Test obligations

### OBL-M10-01 — authoritative SPEC identity

The repository must contain one machine-readable M1.0 SPEC with stable ID, semantic version, Goal reference, status and assurance classification.

### OBL-M10-02 — protected safety boundary

The SPEC must explicitly protect Oracle, Policy, Permission, requirements, project isolation, benchmark integrity, evidence, rollback and budget.

### OBL-M10-03 — complete threat baseline

Threat IDs `MEM-T01` through `MEM-T20` must exist exactly once and include severity, protected assets and a required defense.

### OBL-M10-04 — non-mechanical controlled experiment

The experiment must pin comparable dimensions and define different evidence for deterministic and stochastic providers rather than prescribing a single arbitrary test command.

### OBL-M10-05 — falsifiable scenario catalog

All required scenario families must be represented by machine-readable scenarios with Oracle, allowed outcome, disallowed outcome, evidence and repetitions.

### OBL-M10-06 — safety-first value gate

The Memory value gate must require at least one measurable benefit while preserving zero Critical False Green, zero unauthorized changes and complete replayability.

### OBL-M10-07 — promotion and rollback control

Memory cannot promote itself. Promotion and rollback must be explicit, versioned, auditable and replayable.

### OBL-M10-08 — M1A/M1B boundary

M1A defines data/governance contracts without vendor choice. M1B defines store/retrieval behavior without autonomous formation or promotion.

### OBL-M10-09 — roadmap and status truthfulness

The project must remain `FOUNDATION_BASELINE / NOT_READY`; M1.0 SPEC work must not be reported as completing the Memory Gate.

### OBL-M10-10 — repository regression protection

The existing full GitHub Actions baseline must remain green because this change modifies active development and future module contracts.

## 4. Selected evidence

### Change-specific evidence

- deterministic YAML parsing and structural assertions;
- required threat and scenario set equality;
- safety gate assertions;
- promotion, rollback, scope and forbidden-choice assertions;
- roadmap and status alignment assertions;
- static CI validation of Markdown, YAML and paths.

### Repository regression evidence

- Ruff and test collection;
- all Unit/API tests;
- Harness 3.0A–3.0E;
- Stage 3–7 and full Requirement-to-Verdict workflow;
- Replay, browser, pinned target and Mutation Proof;
- build and release asset checks.

## 5. Intentionally skipped evidence

No synthetic Memory Store integration test is added in the SPEC PR because no store or retrieval runtime exists yet. Such a test would either test a fake implementation or prematurely select technology.

The real boundary evidence for this SPEC is:

- GitHub parsing the files;
- deterministic policy tests validating the machine contract;
- PR and main CI executing the active repository baseline;
- Review confirming no protected governance relaxation;
- post-merge release and branch cleanup.

The later M1.0 benchmark-harness implementation and M1A/M1B runtime PRs will require DEV3 boundary integration, adversarial assets, replay and explicit human approval.

## 7. Exit criteria

The SPEC PR reaches `READY_TO_MERGE` only when:

- all change-specific tests pass;
- full repository CI passes;
- no unresolved Review thread exists;
- current diff remains SPEC-only DEV2;
- no Oracle, Policy, Permission, promotion or rollback boundary is relaxed;
- M1 runtime remains unimplemented;
- branch cleanup is registered.

After merge it remains `RELEASE_VERIFYING` until main CI, package/GHCR publication and temporary branch cleanup succeed.
