# 云端开发用户沟通 SSOT

> 状态：`ACTIVE`  
> 版本：`1.0.0`  
> Goal：Issue #39  
> 适用对象：所有向用户汇报云端开发进度、结果、风险和计划的人类或 AI Agent  
> 机器可读策略：`docs/user-communication-ssot.yaml`

## 1. 目标

用户默认应当用最少的阅读成本理解四件事：

1. 业务上已经解决了什么；
2. 当前真实处于什么状态；
3. 哪些事实、失败、限制或风险会影响判断；
4. 接下来做什么，以及什么才算完成。

简洁不能以牺牲事实为代价。技术细节可以后置，但失败、阻塞、未验证项、未合并、未发布、残余风险和 Human UAT 要求不得隐藏。

## 2. 沟通优先级

默认按以下顺序组织用户可见内容：

```text
业务结果
→ 当前状态
→ 关键事实与边界
→ 下一步计划
→ 必要技术证据
```

业务语言优先回答：

- 用户现在能做什么；
- 系统现在会正确处理什么；
- 哪个业务问题已经解决；
- 哪个问题仍未解决或仍需验证。

PR、Commit、CI、Artifact、Hash、类名、函数名和内部状态机属于支持证据，不应成为默认主叙事。

## 3. 强制状态词

以下状态必须准确区分：

| 状态 | 含义 |
|---|---|
| `PLANNED` | 已有计划，尚未开始实现 |
| `IMPLEMENTING` | 正在实现，结果尚未形成 |
| `IMPLEMENTED` | 已写入分支，但不代表测试通过、已合并或已发布 |
| `VERIFIED` | 规定的验证已通过，但可能尚未合并或发布 |
| `MERGED` | 已进入 `main`，但可能仍在主干或发布验证中 |
| `RELEASED` | 适用的构建或发布已成功 |
| `CLOSED` | Goal、验证、合并、发布、台账和清理等适用环节均已完成 |
| `BLOCKED` | 存在阻塞，不能继续或不能宣称完成 |
| `FAILED` | 当前验证、发布或执行结果失败 |

不得用不带限定词的“已完成”代替上述状态。只有达到 `CLOSED` 时，才可以直接称为“已完成”；其他情况必须说明，例如“实现完成，待验证”或“已合并，待发布验证”。

## 4. 默认表达结构

简单进度更新优先使用一到三句话：

```text
当前结果 + 真实状态。
发现的阻塞或关键事实。
下一步动作。
```

阶段或最终汇报默认最多四个部分：

1. **结论**：一句话说明业务结果和真实状态；
2. **已实现**：最多列出最重要的业务能力；
3. **事实与边界**：只保留影响判断的验证、失败、限制、风险和状态；
4. **下一步**：说明下一项业务目标、目的和完成标准。

内容很简单时，不必机械保留四个标题，可以合并成短段落。

## 5. 业务语言规则

必须先描述业务效果，再补充技术实现。

推荐：

```text
系统现在能识别五类体验退化，五类都已验证通过。
```

必要时再补：

```text
技术证据：5/5 Mutation Killed，Replay 与精确恢复均为 100%。
```

不推荐默认直接输出：

```text
新增了 StateMachine、Manifest、Runner、Artifact Digest 和 28 个 Commit。
```

计划也应使用业务语言：

```text
下一步验证系统是否会误报健康页面；完成标准是健康场景零误报、缺陷场景全部识别。
```

而不是只说：

```text
下一步实现 UX2 Benchmark Harness。
```

## 6. 事实保真规则

为了简洁可以省略低价值过程，但不得省略会改变用户判断的事实。

必须披露：

- 当前生命周期状态；
- 失败、排队中、执行中或未验证的检查；
- 尚未合并、尚未发布或尚未关闭；
- 阻塞、残余风险、已知限制和范围外事项；
- Human UAT、人工批准或外部依赖；
- 与用户预期不一致的结果；
- 不确定性、推断和证据不足。

禁止：

- 把计划描述成已实现；
- 把分支实现描述成已合并；
- 把 PR 验证描述成主干验证；
- 把构建成功描述成生产可用；
- 把部分通过描述成全部通过；
- 为了让汇报更短而隐藏失败或阻塞；
- 用“应该、看起来、大概率”替代可核验事实却不标明推断；
- 重复粘贴长篇工具日志作为用户汇报。

## 7. 技术证据后置

技术证据仅在以下情况默认保留：

- 支撑“已验证、已合并、已发布、已关闭”等关键状态；
- 失败或阻塞需要精确定位；
- 用户需要审计、复现或技术决策；
- 技术限制会改变业务结论。

默认只保留最关键的 PR、Commit、CI Run 或 Artifact。完整日志、文件清单、Hash 列表和内部实现细节放入技术附录，或在用户明确要求时提供。

## 8. 进度更新规则

进度更新只报告相对上一次的有效变化：

- 状态推进；
- 新发现的问题；
- 已解决的阻塞；
- 需要用户决策的事项。

禁止把每次工具调用、文件读取、依赖安装和无变化轮询写成流水账。

## 9. 最终报告规则

最终报告至少回答：

```text
业务结果是什么？
真实交付状态是什么？
用什么关键证据验证？
还有哪些限制或后续工作？
```

证据应支持结论，而不是淹没结论。除非用户要求，默认不重复完整开发过程。

## 10. 例外

用户明确要求以下内容时，可以展开：

- 完整技术实现；
- 全部 Commit、CI、Artifact 和 Hash；
- 逐步调试过程；
- 架构、代码或测试细节；
- 审计或复现报告。

展开时仍必须保持状态真实，不得用技术细节掩盖失败、未验证或范围限制。

## 11. 执行与验证

- `AGENTS.md` 必须将本规范列入强制读取顺序；
- 机器可读规则由 `docs/user-communication-ssot.yaml` 定义；
- `tests/unit/test_user_communication_ssot.py` 验证关键不变量；
- 本规范属于沟通治理，不修改 Oracle、Permission、Release Gate、安全边界或 Autonomous Mandate 范围。
